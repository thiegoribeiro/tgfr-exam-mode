==========================================================================

scripts, earlier release files, screenshots, diagnostic messages and retained
development records. It separates what was requested, what the source code

  SOURCE-REVIEWED: Behaviour is established by the inspected source.
  USER-REPORTED:   Observed by the user in a message, screenshot or log.

  PENDING:         Implementation or acceptance testing remains outstanding.

R01 -- ORIGINAL NETWORK-DISABLING BAT, VERSION 3.2
Date in supplied header: 17 May 2023
Evidence: SOURCE-REVIEWED from the pasted code. [S01]

Purpose
  Attempt to disable Wi-Fi and Windows VPN settings, then restart Windows.

Implementation
  Uses reg add under HKEY_LOCAL_MACHINE and writes a DWORD named Value=0
  at seven PolicyManager\default locations:
    WiFi\AllowAutoConnectToWiFiSenseHotspot
    WiFi\AllowInternetSharing
    WiFi\AllowManualWiFiConfiguration
    WiFi\AllowWiFi
    WiFi\AllowWiFiDirect
    WiFi\WLANScanMode
    Settings\AllowVPN
  Records command failures in a success variable. If every registry command
  succeeds, waits 30 seconds and invokes shutdown /r /t 0.

Development findings
  A successful registry write does not establish that a network adapter or
  VPN client was blocked. The script performs no live enforcement check.
  It saves no original values, types or absence information. A later command
  failure can leave earlier writes applied because there is no rollback.
  It contains no application blocking, Office proofing control, Ethernet
  control, exam-mode toggle or graphical interface.

Status
  Historical predecessor. Its version label belongs to this network utility.


R02 -- PYTHON NETWORK-REVERSAL UTILITY, VERSION 1.0
Date in supplied header: 18 December 2025
Evidence: SOURCE-REVIEWED from the pasted code. [S02]

Purpose
  Reverse the preceding network registry changes and restart Windows.

Implementation
  Uses winreg, ctypes and an administrator check. If necessary, requests
  elevation through ShellExecuteW with the runas verb.
  By default writes DWORD Value=1 at the same seven registry paths.
  Optional REVERT_TO_NOT_CONFIGURED=True deletes each Value instead.
  On reported success, waits 30 seconds before shutdown /r /t 0; Ctrl+C
  cancels the wait/restart stage.

Development findings
  Writing 1 everywhere cannot reconstruct a machine's original values.
  Deleting values is also not an exact restore without an earlier snapshot.
  The script labels deletion as Not configured without verifying effective
  Windows policy. Neither operation checks actual Wi-Fi/VPN availability.
  The deletion helper ignores an absent value within an existing key, but an
  absent key reaches the outer OSError handler and is reported as failure.
  Elevation and restart return values are not fully checked by this code.

Status
  Historical reversal utility. Its shortcomings motivated recording the
  original state before applying exam restrictions.


R03 -- EXAM MODE 3.0, PYTHON IMPLEMENTATION
File: TGFR_Exam_Mode_v3.py
Date: No source release date; documented by 20 November 2026.
Evidence: SOURCE-REVIEWED. [S03]

Added behaviour
  Provides on, off and status console commands with ENABLE and RESTORE
  confirmation prompts. The source describes reversible per-user Windows
  configuration and a convenience policy.
  Adds calc.exe, CalculatorApp.exe and EXCEL.EXE to the current user's
  Explorer DisallowRun list and enables the DisallowRun switch.
  Writes these Word 16.0 preference values as DWORD zero:
    CheckSpellingAsYouType
    CheckGrammarAsYouType
    CheckGrammarWithSpelling
  No Wi-Fi, VPN, Ethernet or Microsoft Store control is implemented here.

Backup and restore
  Path: %LOCALAPPDATA%\TGFR_Exam_Mode\original_registry_values.json
  Schema version: integer 3.
  Records prior registry existence, value and type, plus created keys and
  added rules. Uses exclusive backup creation before writes, checks written
  values and attempts rollback after an apply failure.
  Successful restore removes the backup; incomplete restore retains it.
  There is no automatic restart; the operator is told to sign out/in and
  test the resulting behaviour.

Limits and review notes
  Registry status is not a real application launch test.
  Word preferences do not set the document's NoProofing property.
  Unlike the BAT v3 implementation, the backup has no user SID validation.
  The created-key cleanup calls DeleteKey without an explicit values-count
  check; it should be reviewed before treating cleanup as empty-key-only.
  The status command returns success even when its displayed match checks
  are false. These last points are source-review findings, not recorded
  Windows test failures.


R04 -- EXAM MODE 3.0, STANDALONE BAT IMPLEMENTATION
File: TGFR_Exam_Mode_v3.bat
Date: No source release date; documented by 20 November 2026.
Evidence: SOURCE-REVIEWED. [S04]

Change from the Python implementation
  Packages an embedded Windows PowerShell payload inside a BAT launcher.
  Python installation is no longer required for this variant.
  Retains on/off/status, console confirmation, the same three application
  names and the same three Word preference settings.
  Still contains no Wi-Fi, VPN, Ethernet or Store controls.

Backup and restore
  Path: %LOCALAPPDATA%\TGFR_Exam_Mode\original_registry_values_bat.json
  Schema fields include version=3, format=TGFR-BAT, userSid, createdKeys
  and changes. This format is distinct from the Python v3 backup.
  Uses exclusive FileMode.CreateNew and flushes the backup before writes.
  Validates the version, format and current user's SID before restoring.
  Restores recorded changes in reverse order. Cleanup explicitly checks
  that a created key has no values or subkeys before deleting it.

Limits
  Application controls are still Explorer executable-name restrictions.
  Registry verification does not prove an app launch is blocked.
  The status command can print mismatches while returning exit code zero.
  No document-level or suite-wide Office proofing lock is implemented.
  Python and BAT v3 state files must not be interchanged.


R05 -- EXAM MODE GUI 4.0
File: TGFR_Exam_Mode_GUI_v4.bat
Date: No source release date; documented by 20 November 2026.
Evidence: SOURCE-REVIEWED. [S05]

Added features
  Introduces a Windows Forms GUI through embedded PowerShell in STA mode.
  Provides five selectable restrictions: Wi-Fi, Windows VPN settings,
  Calculator, Excel and automatic Word spelling/grammar.
  All five options initially appear checked. Actions are Enable Exam Mode,
  Restore Original State and Refresh Status.
  Uses a fixed-dialog 610 x 545 window without a maximise button.

Networking
  Detects physical Wi-Fi adapters by medium/name/description and records
  enabled adapters before disabling them with Disable-NetAdapter.
  Tracks adapter description/name; restore enables by description.
  Selecting Wi-Fi when no enabled wireless adapter is found raises an error.
  VPN continues the earlier HKLM PolicyManager\default\Settings\AllowVPN
  Value=0 write. Its source explicitly notes this is not a reliable effective
  MDM-policy location. Ethernet is not implemented in this release.

Applications and Word
  Retains per-user DisallowRun for Calculator and Excel.
  Adds HideSpellingErrors=1 and HideGrammarErrors=1 to the three existing
  Word preference values. These remain preferences, not document NoProofing.

State and operating model
  Path: %LOCALAPPDATA%\TGFR_Exam_Mode_GUI\original_state.json
  Journal version: string 4.0; includes user SID, selections, registry
  changes and wifiAdapters. Requires elevation under the intended account.
  Records the baseline before writes, attempts rollback on failure and
  prevents enabling a second session over an existing snapshot.
  Restore checks the account SID and retains the backup if errors occur.

Limitations
  Fixed positioning constrains the display on smaller or scaled desktops.
  Refresh Status primarily reports saved-session existence.
  Registry restoration does not check for later external value changes.
  Wi-Fi restore uses descriptions rather than stable adapter GUIDs.
  No Store option or comprehensive application launch enforcement is present.

R08 -- EXAM MODE GUI 6.0
File: TGFR_Exam_Mode_GUI_v6.bat
Recorded development date: 20 November 2026
Evidence: SOURCE-REVIEWED, retained development tests and user report. [S08]

Reason for the release
  Address Calculator enforcement, the Word proofing requirement, restoration
  reliability and the clipped interface reported after v5.

Application controls
  Replaces the main application's executable-name approach with AppLocker
  planning, application of local rules and effective-policy verification.
  Calculator and Store use package publisher rules; Calculator also uses
  discovered modern/classic executable identities and paths.
  Excel uses detected desktop executable paths and publisher/hash identities.
  The operator explicitly selects the exam account SID. Applications must
  be closed before applying the relevant restrictions.
  Verification checks rule presence, enforcement, Application Identity
  service status and explicit Denied predictions for the target account.

Word workflow
  Replaces the broad Office-proofing checkbox with Prepare Word exam copy.
  Creates a new blank .docx or a separate copy of a supported source .docx.
  Applies w:noProof to supported text runs, paragraph marks, styles and
  defaults, then verifies the resulting package.
  Preserves the source file and retains the exam copy/student work on restore.
  This is document-level formatting, not a lock across the Office suite.

Network and restoration redesign
  Records physical Wi-Fi/Ethernet adapter GUIDs and original administrative
  state. Already-disabled adapters remain disabled on restoration.
  Changes the VPN option to the selected user's SettingsPageVisibility for
  the VPN settings page. It does not claim to block VPN traffic or clients.
  Uses a protected machine-wide v6 session journal saved before mutations.
  Tracks attempted steps, attempts rollback after apply failure, restores
  networking before later recovery steps, and keeps incomplete recovery data.
  Adds recovery of recognised v4/v5 backups, including known legacy
  Calculator interception values, while validating privileged destinations.

Interface and distribution
  Keeps the single BAT distribution with embedded Windows PowerShell 5.1.
  Adds a resizable, DPI-aware, tabbed layout, scrollable content and a docked
  action/status footer. Tabs cover Restrictions, Word exam document and
  Diagnostics. Adds Verify, Copy diagnostics, account selection and previous
  version recovery. Provides help, verify, restore and recover-v5 actions.
  The release does not schedule an automatic restart.

Defects discovered after delivery
  A startup position expression raises System.Object[] op_Addition.
  A nested event callback later loses the UI state reference.
  The AppLocker preflight rejects any local/effective policy difference,
  including compatible domain policy. These are addressed in R09/R10.


R09 -- EXAM MODE GUI 6.0.1
File: TGFR_Exam_Mode_GUI_v6_0_1.bat
Recorded development date: 20 November 2026
Evidence: SOURCE-REVIEWED diff and DEV-TESTED regression. [S09, S11, S13]

Reported error
  Method invocation failed because [System.Object[]] does not contain a
  method named 'op_Addition'.

Root cause and correction
  The form's Shown handler used arithmetic inside a New-Object Point(...)
  expression. PowerShell parsed part of the comma-separated expression as
  an array instead of two scalar coordinates.
  The fix calculates separate typed integer windowLeft/windowTop values,
  then constructs [System.Drawing.Point]::new(windowLeft, windowTop).
  It also groups the Generated diagnostics-header expression correctly.

Validation and compatibility
  The original error was reproduced, then the updated handler passed ten
  screen/monitor positioning cases and a diagnostic-header check.
  The saved v6 state format and application/network/Word engine behaviour
  remain unchanged by this patch. Earlier v6 backups stay compatible.
  Native Windows rendering was not executed in the development environment.

Subsequent feedback

  action, followed by the VerificationLines error and AppLocker policy
  message documented under R10.


R10 -- EXAM MODE GUI 6.1
File: TGFR_Exam_Mode_GUI_v6_1.bat
Recorded development date: 20 November 2026
Evidence: SOURCE-REVIEWED and DEV-TESTED; Windows acceptance PENDING.
Sources: [S10, S12, S13, S14]

Fix A: VerificationLines callback state
  The Verify click handler's nested GetNewClosure did not retain the outer
  callback's UI-state reference. The inner operation could therefore access
  null even though the original state had a VerificationLines member.
  The shared operation wrapper now explicitly passes persistent window
  state and a request-data hashtable to the operation.
  Verify updates the supplied state and Diagnostics tab. Enable receives
  account SID, selected options and Word paths explicitly. Restore and
  legacy recovery follow the same operation signature.
  Diagnostic failures now include the script stack location.

Fix B: Existing domain AppLocker policies
  Removes the requirement that local and effective policy be identical.
  Saves originalLocalXml and originalEffectiveXml separately, plans against
  effective policy and writes the local changes only.
  Existing enforced collections receive target-account deny additions only.
  Domain allow rules are not copied into local policy, and existing effective
  allowlists do not receive a new allow-all rule.
  Handles nonempty NotConfigured/omitted-mode collections as enforced.
  Reports effective AuditOnly with the exact collection state instead of
  the previous general domain-policy rejection. [M01, M02]

Preservation and verification refinements
  Creates an allow-other baseline only where the affected collection was
  genuinely unrestricted. Preserves a pre-existing implicit packaged-app
  block when EXE enforcement exists without Appx rules.
  Separately checks for local and effective snapshot changes before apply.
  Verification compares external rules in each touched collection with
  their original effective baseline, excluding TGFR-owned rule IDs.
  This detects missing original allowances, newly arriving allowlists and
  changed external rules. Unrelated untouched collections may change.
  A detected change reports that the plan needs restoration/review/refresh
  and reapplication. Verification does not rewrite domain policy.
  These are checks at operations/verification, not continuous monitoring.

Restore and diagnostics
  Restores the recorded local policy without restoring domain policy.
  Preserves independent changes and retains the current Application Identity
  service configuration where new effective rules would make reverting it
  inappropriate; Diagnostics explains this exception to exact restoration.
  Logs source summaries and collection modes/rule counts.
  Normalises harmless GUID casing and XML ordering differences for comparison.
  Corrects XML-node name handling to use LocalName where appropriate.
  Retains MDM/CSP and service-prerequisite checks.

Compatibility
  Machine journal schema remains version 6, at the same path.
  Older v6/v6.0.1 AppLocker plans without originalEffectiveXml fall back to
  originalLocalXml, matching those versions' local/effective equality check.
  The 6.0.1 startup correction, resizable interface, network controls, Word
  exam-copy workflow and legacy recovery remain included.

Recorded validation
  72 AppLocker assertions with simulated Windows policy/service responses.
  24 engine backup/apply/rollback/restore assertions.
  Five UI callback groups and the ten positioning cases plus header check.
  Final BAT payload syntax, help execution and function visibility checks.
  See section 6 for exact limits of this evidence.

Subsequent user report
  The user ran v6.1 and reported the stopped Application Identity safeguard
  at 12:49:58 and 12:57:24, with diagnostics generated at 12:58:37 on
  20 November 2026. This stopped the selected application-control operation
  in preflight. The log does not contain the policy collection modes needed
  to determine whether the refusal was necessary for that exact machine.
  The resulting investigation and patch are recorded under R11. [S15]


R11 -- EXAM MODE GUI 6.1.1
File: TGFR_Exam_Mode_GUI_v6_1_1.bat
Recorded development date: 20 November 2026
Evidence: SOURCE-REVIEWED and DEV-TESTED; Windows acceptance PENDING.
Sources: [S15-S17, M09, M10]

Reason for the patch
  The user reports that v6.1 still cannot enable the selected restrictions:
  Application Identity is stopped while existing effective AppLocker rules
  are present. The stack reaches Assert-TgfrAppServiceCanStart.
  This is an intentional application safeguard, not evidence of a failed
  Start-Service command or the earlier VerificationLines callback defect.

Fix A: Service preflight distinguishes policy configuration
  The old guard refused any existing rule while the service was not running.
  The updated guard examines effective collection type, enforcement mode,
  rule count and unsupported extensions before deciding whether starting a
  stopped service could activate existing enforced collections.
  Known audit-only or empty existing collections no longer fail solely for
  being present. Requested collections configured AuditOnly still cannot
  be presented as enforced exam restrictions by the planning/verification
  logic. Nonempty Enabled/NotConfigured collections remain a reason to
  refuse automatic activation while the service is stopped.
  Disabled startup, transitional service states, unknown types/modes and
  unsupported extensions receive specific diagnostic messages.
  This does not establish that the user's current policy is safe to activate;
  its actual exported policy and service state must be reviewed.

Fix B: Diagnostic ordering
  Local/effective policy summaries and the service status/startup snapshot
  are logged before the service safeguard can throw. Previously these facts
  could be returned only after a complete plan had been built, leaving a
  failed preflight log with little more than the error and stack trace.
  Apply rechecks startup metadata and service state before the first policy
  write, alongside the existing independent policy-snapshot checks.

Fix C: Preserve service startup settings for new sessions
  New AppLocker plans record serviceStartupPolicy=Preserve and do not change
  AppIDSvc startup type or delayed-start metadata. They may start a stopped,
  enabled service only after the preflight permits it; starting the service
  and changing its configured startup type are separate operations.
  Restore leaves this session's startup baseline intact and preserves any
  later outside change. The protected service may remain running until a
  restart; the app does not claim exact restoration of its running state.
  Microsoft documents that sc.exe cannot reset protected AppIDSvc to Manual.
  Older journals whose Manual baseline is already present need no startup
  command. If an older release changed it away from Manual, restoration now
  reports the limitation and retains recovery data instead of attempting an
  unsupported start=demand command or overwriting protected Start values.
  Other supported legacy restoration paths remain separately guarded.

Read-only diagnostic collector
  Adds diagnostics.ps1 with Invoke-TgfrDiagnosticExport as a separate
  diagnostic component, distributed as TGFR_Exam_Mode_Diagnostics_v1.bat.
  It records Windows edition/build, separately labelled
  operator/interactive accounts, AppIDSvc status/startup, local/effective
  AppLocker XML and collection counts, named Calculator/Store packages,
  Excel App Paths and MDM-presence indicators only. Optional CiTool -lp -json
  captures App Control policy inventory when that tool is available.
  It writes a unique report directory, continues after section-level errors,
  and does not change policy, service, registry, network or file permissions.
  It distinguishes missing evidence from an empty policy and does not infer
  the owning GPO from a local/effective difference. A stopped service alone
  is not reported as proof that cached enforcement is absent. [M10]

Compatibility and scope
  Machine journal schema remains version 6. Historical sessions remain
  readable; protected-service limitations are reported during recovery.
  AppLocker remains the app's application-control backend. Alternatives
  such as App Control for Business were researched and compared, but no
  WDAC/App Control backend is implemented by this patch. Reverting to v4.1
  registry restrictions would retain their earlier coverage limitations.

Recorded validation at this journal update
  95 AppLocker assertions and 24 engine assertions passed using simulated
  Windows boundaries. Five UI callback scenarios plus startup arithmetic
  and diagnostic-header regression checks also passed on PowerShell/Linux.
  20 read-only collector assertions passed, including XML classification,
  safe parsing, report interpretation and a bounded read-only AST guard.
  These counts do not establish Windows launch enforcement or successful
  native collection. The collector's Windows entry point was not executed
  by those tests. Both final packaged payloads parsed and their help-only
  actions executed successfully. BAT marker/ASCII/CRLF checks passed. Built
  release fingerprints appear in section 11.


R12 -- EXAM MODE GUI 7.0
File: TGFR_Exam_Mode_GUI_v7.bat
Recorded development date: 20 November 2026
Evidence: SOURCE-REVIEWED and DEV-TESTED; native Windows acceptance PENDING.
Sources: [S18-S21, M12-M16]

Reason for the architecture change
  The user's follow-up screenshot shows the more precise v6.1.1 refusal:
  Application Identity status is Stopped. Existing enforced collections:
  Appx=Enabled/2 rules; Exe=NotConfigured/4 rules. Starting the service could
  activate these existing restrictions. The user then explicitly asks that
  the code stop using the previous application-control backend. This is no
  longer treated as an audit-only false positive to bypass. [S18]

Implemented backend replacement
  The new app_control.ps1 uses App Control for Business (WDAC), the Windows
  ConfigCI compiler and native CiTool. It builds a separate unsigned base
  policy with a unique owned GUID. It does not import the earlier backend,
  invoke its commands, inspect its rule collections or configure its service.
  Existing App Control policy identities are inventoried independently and
  preserved. The tool updates/removes only its recorded owned policy ID.
  It has no Managed Installer or reputation-based dependency in this policy.

  Calculator and Store use their Package Family Names. A Windows 11 wildcard
  package allow baseline preserves other package families within this new
  policy, alongside narrow selected-package denies. Desktop Excel and
  discovered classic Calculator executables receive narrow file-identity
  rules or explicit hash fallback. The policy validator rejects broad
  publisher denies and missing user/kernel allow baselines. It also checks
  the intended options, IDs, signing state and compiled fingerprints.
  This is a standalone deny-policy design; it does not merge broad allows

v6 machine journal
  Active file: %ProgramData%\TGFR_ExamMode_v6\session.json
  Schema version: integer 6, including in app releases 6.0.1, 6.1 and 6.1.1.
  Main fields: sessionId, machineId, createdUtc, targetSid, options, phase,
               appPlan, appAttempted, registryChanges, adapters and word.
  Recorded phases: Prepared, Applying, Active, Restoring, Recovery required,
                   and Restored (archived).
  The directory is restricted to Administrators and SYSTEM. State writes use
  temporary files and atomic replacement. A machine mutation lock serialises
  apply/restore operations. Existing active snapshots cannot be overwritten.
  A successful restoration archives the journal; an incomplete restoration
  retains the active recovery information.

What restoration means
  It restores the state that this session recorded for the settings it
  touched. It is not an image backup or Windows System Restore point.
  Registry comparisons include value type and existence, not just data.
  Adapters are matched by GUID and restored to the recorded enabled/disabled
  state. The selected account's registry hive must be available when needed.
  Application restoration changes local policy only. Conflicting edits to
  touched local policy are preserved and reported for reconciliation.
  New v6.1.1 sessions preserve AppIDSvc startup configuration. The protected
  service may remain running until Windows restarts. Older sessions receive
  guarded recovery; a Manual baseline changed by an older release may need
  owning-policy reconciliation because sc.exe cannot reset it to Manual.
  Outside startup changes and policy requirements are preserved and reported.
  Word exam copies and candidate answers are retained.

Compatibility map

  BAT v3:    TGFR-BAT format and original_registry_values_bat.json file.
  GUI v4/4.1/v5: recognised legacy original_state.json formats, recoverable
                through the v6 previous-version recovery path where valid.

J-015 -- Cross-edition testing reported on 26 November 2026
Evidence: USER-REPORTED, without supporting sanitised run logs.

The tester reported partial passes on Windows 10 Home 22H2 and Windows 11
Home 24H2. Wi-Fi, Ethernet and the VPN option passed; blocking desktop

proof of either Home support or edition-wide impossibility.

not independently confirmed), the tester reported all other selected
features passing, but Word spelling checking remained active. This needs
document-level and native desktop Word investigation, not an unverified
claim of complete Office-wide proofing enforcement.

TGFR BAT 3.2 script that writes PolicyManager default and current/device
registry values and schedules a restart. Record that as PROPOSED only:
a registry write does not establish adapter enablement or VPN reachability,
and directly overwriting default/managed policy values without capturing
the baseline would break the current restoration guarantees. Prefer the
existing exact-state restore workflow; any new compatibility repair must be
opt-in, policy-aware, journalled, per-write verified and restart-safe.

No change was made to application code in response to this report.
The latest published executable remains 7.0.2 experimental; the exact
test executable hash and Windows editions/builds remain unconfirmed.
